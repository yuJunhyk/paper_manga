### 2.4 무엇을 (What)

연구 논문 PDF 한 편을 올리면 서버가 논문 내용을 읽고, 만화처럼 **컷 단위로 나눈 대본**을 만들어 보여 줍니다.

**MVP 범위 (2026-09-24 확정)**

MVP(Minimum Viable Product)는 "핵심 가치를 확인할 수 있는 최소 기능 제품"입니다. 이 프로젝트의 MVP에 포함할 것과 뺄 것은 다음과 같습니다.

| 구분 | 내용 | 비고 |
| --- | --- | --- |
| 입력 | 연구 논문 PDF **전체** | 초록만 받는 방식도 검토했지만, 전체 입력으로 결정 |
| 출력 | 컷별 **글 대본**(장면 설명, 대사 등 텍스트) | 그림은 만들지 않음 |
| 원문 근거 | 각 컷에 "이 내용이 논문 어디에서 나왔는지" 원문 근거를 붙임 | 평소에는 숨기고, **버튼을 눌러야** 보임 |
| 저장 | 변환 결과를 **DB에 저장** | |
| 처리 방식 | **비동기 처리**. 요청 직후 결과를 기다리지 않고, 상태를 조회 | 상태: 대기 → 처리 중 → 완료 |
| 로그인 | MVP에서는 **제외** | 이후 단계에서 검토 |
| 그림(이미지) | MVP에서는 **제외** | 대본을 바탕으로 사용자가 직접 AI 이미지 도구로 생성 |

### 2.5 왜 (Why)

**1) 포트폴리오 목적: 백엔드 역량 증명**

이 프로젝트의 1차 목적은 금융권 Java/Spring 백엔드 취업용 포트폴리오입니다. 그래서 그림 품질이 아니라 아래와 같은 **백엔드 설계**를 보여 주는 데 집중합니다.

- 오래 걸리는 작업(논문 분석)을 **비동기로 처리**하고, 상태를 관리하는 구조
- 요청, 처리 상태, 결과를 저장하는 **DB 설계**
- 외부 도구(PDF 추출기, AI 모델)와 연동하는 구조

이미지 생성을 MVP에서 뺀 것도 이 때문입니다. 그림 품질을 올리는 작업은 백엔드 역량을 보여 주는 데 큰 도움이 되지 않습니다.

**2) 서비스 차별점: 논문 특화 + 원문 근거**

비슷한 서비스(LlamaGen, StudyGlen 등)도 있지만, 이 프로젝트는 다음 두 가지가 다릅니다.

- **논문 특화:** 범용 PDF가 아니라 연구 논문만 대상으로 합니다. 논문은 제목, 초록, 본문, 참고문헌처럼 구조가 비교적 정해져 있어서 그 구조를 활용할 수 있습니다.
- **원문 근거 표시:** AI가 만든 대본은 논문에 없는 내용을 지어낼 수 있습니다(환각). 각 컷에 원문 근거를 붙여 두면 사용자가 버튼 하나로 직접 확인할 수 있습니다.

### 2.6 어떻게 (How)

프로젝트는 아래 단계로 진행합니다. 1단계 이후의 세부 설계는 앞 단계 결과를 보고 정합니다.

**1단계. PDF 텍스트 추출 기술 검증 (완료, 2026-10-02)**

논문 PDF에서 글자를 제대로 뽑아낼 수 있어야 이후 작업이 가능합니다. 그래서 본 개발 전에 추출 도구 두 가지를 같은 논문으로 비교합니다.

- [x] Apache PDFBox 3.0.5로 샘플 논문 1페이지 텍스트 추출 (`spikes/pdfbox-spike`)
- [x] PDFBox로 샘플 논문 2편 전체 추출 후 품질 기록
- [x] GROBID 0.9.1(경량 CRF 이미지)로 같은 논문 추출 (`spikes/grobid-spike`)
- [x] 두 결과를 비교해 사용할 방식 결정 → **GROBID로 결정** (2026-10-02)

비교할 때 볼 점(예정):
- 2단 편집 논문에서 읽는 순서가 올바른가
- 제목, 초록, 섹션 구분 같은 **논문 구조**를 알아낼 수 있는가
- 수식, 표, 그림 캡션, 참고문헌이 본문과 섞이지 않는가
- 원문 근거 표시에 쓸 **위치 정보**(페이지, 문단 등)를 얻을 수 있는가

**비교 결론**

- 원문 근거 표시에 필요한 **문장 단위 구분**과 **페이지·위치 정보**는 GROBID만 바로 제공합니다. PDFBox로 같은 결과를 얻으려면 잡음 제거, 줄 → 문장 이어 붙이기, 제목 판별, 페이지 추적을 모두 직접 구현해야 합니다.
- GROBID의 약점은 **수식 내용이 깨진다**는 점과 **제목 인식 오류가 가끔 있다**는 점입니다. 수식은 대본 생성에서 핵심이 아니고, 제목 오류는 주로 부록에서 생겨서 MVP에 주는 영향은 작습니다.
- GROBID를 쓰면 Docker로 GROBID 서버를 따로 띄워야 하고, Spring 서버가 이 서버를 HTTP로 호출하는 구조가 됩니다. 운영할 서버가 하나 늘어나는 대신, 외부 서비스 연동이라는 백엔드 설계 경험을 쌓을 수 있습니다.

**2단계. Spring 백엔드 MVP 구현 (진행 중)**

- [x] Spring Boot 프로젝트 생성 (`backend/`, Spring Boot 4.1.1, Java 25, Gradle)
- [x] PDF 업로드 API `POST /api/papers` (업로드 크기 제한 50MB)
- [x] GROBID 연동: Spring 서버가 GROBID를 HTTP로 호출 (`GrobidClient`, 주소는 `application.properties`의 `grobid.url`)
- [x] GROBID 결과(TEI XML)를 제목 → 섹션 → 문장(페이지 포함) JSON으로 변환 (`TeiParser`). latent-diffusion 논문 기준 섹션 36개(초록 포함), 문장 383개
- [x] Docker Compose(`compose.yaml`)로 PostgreSQL 17과 GROBID를 함께 실행
- [x] Spring 서버를 PostgreSQL에 연결 (Spring Data JPA, PostgreSQL 드라이버, `ddl-auto=update`)
- [x] 변환 작업과 상태를 DB(`paper_job` 테이블)에 저장. 상태는 대기(`PENDING`) → 처리 중(`PROCESSING`) → 완료(`COMPLETED`)이고, 실패를 기록하려고 `FAILED`를 추가함. 작업 조회 API `GET /api/papers/{id}`
  - 구조: Controller(요청·응답) → Service(업무 흐름) → Repository(DB 저장·조회) 3계층
- [x] 변환 작업을 비동기로 처리 (`@Async`, `PaperJobProcessor`). 업로드는 즉시 202(접수됨)와 작업 번호를 돌려주고, 상태 조회 `GET /api/papers/{id}`, 결과 조회 `GET /api/papers/{id}/result`. 결과는 `paper_job.result_json`에 JSON 글자로 저장

  - **비동기 파이프라인**(`PaperJobProcessor`): 업로드 → ① 논문 분석(GROBID, 문장 저장) → ② 핵심 사실 추출(qwen3) → ③ 대본 쓰기(exaone) → ④ 만화 저장 → 완료. 오래 걸리는 AI 호출은 트랜잭션 밖에서, 저장만 짧은 트랜잭션으로
  - **상태와 단계를 나눔**: 상태(대기/처리 중/완료/실패) + 단계(`JobStage`: 논문 분석/핵심 사실 추출/대본 쓰기/완료) + 진행률(`progressDone/progressTotal`, AI 요청 하나가 끝날 때마다 갱신). 진행률은 `JobProgress`가 매번 DB에서 새로 읽어 바꿈(오래 들고 있던 작업 객체로 최신 기록을 덮어쓰지 않게). 실패하면 어느 단계에서 멈췄는지 남김
  - API: `GET /api/papers/{id}`(상태·단계·진행률), `GET /api/papers/{id}/comic`(쪽·컷·대사·근거 원문). 만드는 중이면 409, 만화가 없으면 404

## 3. 용어 설명

| 용어 | 설명 |
| --- | --- |
| MVP | Minimum Viable Product. 핵심 가치를 확인할 수 있는 최소한의 기능만 담은 첫 버전 |
| 스파이크(Spike) | 본 개발 전에 "이 기술이 쓸 만한가"를 짧게 시험해 보는 실험용 작업. 결과 코드는 버려도 되고, 얻은 **판단 근거**가 목적 |
| PDF 텍스트 추출 | PDF 파일 안의 글자를 프로그램이 다룰 수 있는 문자열로 꺼내는 작업. 논문은 2단 편집, 수식, 표가 많아 생각보다 어려움 |
| Apache PDFBox | PDF를 읽고 다루는 Java 라이브러리. 텍스트를 빠르게 뽑을 수 있지만, 논문의 구조(제목/본문/참고문헌 구분)까지는 알려 주지 않음 |
| GROBID | 학술 논문 PDF를 분석해 제목, 저자, 초록, 섹션, 참고문헌 등을 **구조화된 데이터(XML)**로 뽑아 주는 도구. 보통 Docker로 서버를 띄워 사용 |
| Docker | 프로그램을 실행 환경째 묶어 어디서나 똑같이 실행할 수 있게 해 주는 도구 |
| 대본 | 만화의 각 컷에 들어갈 장면 설명과 대사를 글로 적은 것. 이 서비스의 결과물 |
| 원문 근거 | 대본의 특정 컷이 논문의 어느 부분을 바탕으로 만들어졌는지 보여 주는 원문 인용 |
| 환각(Hallucination) | AI가 사실이 아니거나 원문에 없는 내용을 그럴듯하게 지어내는 현상 |
| 비동기 처리 | 요청을 받자마자 "접수됐다"고만 응답하고, 실제 작업은 뒤에서 진행하는 방식. 사용자는 나중에 상태를 조회해 결과를 받음. 논문 분석처럼 오래 걸리는 작업에 적합 |
| 작업 상태 | 비동기 작업의 진행 단계. 이 프로젝트에서는 **대기 → 처리 중 → 완료**로 진행하고, 실패하면 **실패**로 기록 |

## 4. 서비스 사용 흐름 (예시 시나리오)

MVP 기준으로 사용자가 겪는 흐름입니다. API 이름이나 화면 형태 같은 구체적인 모습은 **미정**이며, 아래는 흐름 이해를 돕기 위한 예시입니다.

1. **업로드:** 사용자가 읽고 싶은 논문 PDF(예: Latent Diffusion 논문)를 올립니다.
2. **접수:** 서버는 파일을 받자마자 작업 번호를 돌려주고, 작업 상태를 **대기**로 DB에 저장합니다. 사용자는 기다리지 않고 바로 응답을 받습니다.
3. **처리:** 서버가 뒤에서 작업을 시작하면 상태가 **처리 중**으로 바뀝니다.
   - PDF에서 텍스트를 추출합니다.
   - 추출한 내용을 바탕으로 컷별 대본을 만들고, 각 컷에 원문 근거를 연결합니다.
4. **완료:** 결과를 DB에 저장하고 상태를 **완료**로 바꿉니다.
5. **상태 조회:** 사용자는 작업 번호로 상태를 확인하다가, 완료되면 결과를 봅니다.
6. **결과 확인:** 컷별 대본이 순서대로 나옵니다. 어떤 컷의 내용이 의심스러우면 **근거 보기 버튼**을 눌러 논문 원문을 확인합니다.
7. **(선택) 그림 만들기:** 사용자는 대본을 가지고 원하는 AI 이미지 도구에서 직접 그림을 만듭니다. 이 단계는 서비스 밖에서 이루어집니다.

예시 결과(형태 예시일 뿐 실제 출력 아님):

```
[컷 1]
장면: 연구실. 고해상도 이미지를 만드느라 컴퓨터가 과열되고 있다.
대사: "픽셀 단위로 이미지를 만들면 계산량이 너무 많아!"
[근거 보기] → (논문 원문 해당 문단)
```

```
        ├── ai/            # Ollama 연결 (데스크탑 → 맥북 자동 전환)
        └── comic/         # 만화 저장·조회 (만화 → 쪽 → 컷 → 대사, 컷 ↔ 근거 문장)
            ├── plan/      # 핵심 사실 추출: 조각 나누기, 조각 제목, 사실과 근거 번호 (qwen3)
            └── write/     # 대본 쓰기: 이야기 뼈대, 사실 컷, 연출 컷, 대사 검사 (exaone)
```

- **samples/:** 추출 품질을 비교할 논문을 모아 둡니다. 저작권과 용량 문제로 PDF 파일은 `.gitignore`에 넣어 저장소에 올리지 않습니다. 파일명 끝의 숫자는 arXiv 논문 번호입니다.
- **results/:** Spring API로 받은 결과(논문 분석, 만화 설계도, 완성된 만화)를 `날짜_무엇_작업번호` 이름으로 보관합니다.
- **spikes/:** 본 서비스 코드가 아니라 기술 검증용 실험 코드입니다. 본 서비스 개발에는 쓰지 않고 기록용으로 남겨 둡니다. 시험 결과는 차수별 폴더에 있습니다.
- **backend/:** 본 서비스(Spring 백엔드) 코드입니다. 테스트는 `src/test/`에 있습니다(37개).

## 6. 확정 사항과 미정 사항

### 확정

- 연구 논문 전용 서비스
- 입력은 논문 PDF 전체
- 출력은 컷별 글 대본이며, 이미지는 생성하지 않음
- 컷마다 원문 근거를 붙이고, 버튼을 눌러야 보이게 함
- DB 저장 + 비동기 처리(대기/처리 중/완료 상태 조회)
- 로그인은 MVP에서 제외
- 백엔드는 Java/Spring 기반
- PDF 추출 도구는 GROBID(0.9.1 경량 CRF 이미지). Docker로 띄우고, Spring 서버가 HTTP로 호출 (2026-10-02 확정)
- DB는 PostgreSQL. Docker로 띄움 (2026-10-02 확정)
- 대본 생성 AI는 **무료 로컬 모델**(Ollama). 유료 API는 쓰지 않음. AI 호출 부분은 설정만 바꿔 다른 모델로 교체할 수 있게 만듦 (2026-10-02 확정)
- 모델은 단계마다 나눠 씀: **핵심 사실 추출 = qwen3:8b**(형식을 잘 지킴), **대사 쓰기 = exaone3.5:7.8b**(글을 잘 씀) (2026-10-03, 4·5차 시험으로 확정)
- 대본은 **한국어**, Why책 같은 학습 만화 형식. 분량은 **3~4쪽, 쪽당 6~8컷**(총 약 20~30컷). 처음 정한 4~8컷은 qwen3:8b 시험 결과 너무 짧아서 바꿈 (2026-10-02 확정)
- 등장인물은 **고정 캐릭터 2명**: 질문하는 호기심 많은 학생, 설명하는 박사님 (2026-10-02 확정)
- 컷은 **사실 컷**과 **연출 컷**으로 나눔. 사실 컷은 사실 하나를 전하고 근거 문장을 코드가 붙임(해설도 검증된 사실 문장 그대로). 연출 컷은 쪽마다 여는 컷·닫는 컷 2개이고 근거가 없음. 처음 정한 'AI가 비유로 표시' 방식은 3차 시험에서 근거를 피하는 구멍이 되어 바꿈 (2026-10-03)
- 생성 순서(7차 방식): ① 코드가 본문을 섹션 경계로 12조각(쪽당 3조각)으로 나눔 → ② 조각마다 제목과 핵심 사실·근거 번호를 고름(한계·결론 조각은 사실 3개, 그중 하나는 한계) → ③ 기승전결 이야기 뼈대 → ④ 사실 컷을 하나씩 쓰고 쪽마다 연출 컷 2개 → ⑤ 검사해서 문제가 있으면 다시 쓰기 (2026-10-03 확정)
- 비동기 처리는 Spring `@Async`. 작업에 상태(대기/처리 중/완료/실패)와 단계(논문 분석/핵심 사실 추출/대본 쓰기/완료), 진행률을 기록 (2026-10-03)
- DB 테이블 7개: 작업, 논문 문장, 만화, 쪽, 컷, 대사, 컷 ↔ 근거 문장 연결 (2026-10-03)
- 보안: Spring·PostgreSQL·GROBID는 이 맥북 안(127.0.0.1)에서만 접속. 데스크탑 Ollama는 집 네트워크 안에서만 열고 공유기 포트 포워딩은 하지 않음 (2026-10-03). 사설 IP·비밀번호는 git에 올리지 않음(`.env`) (2026-10-04)
- AI 서버 연결: **데스크탑(RTX 4060 Ti)의 Ollama를 먼저 쓰고, 응답이 없으면 맥북의 Ollama로 자동 전환**. 맥북은 같은 모델이라 품질은 같고 약 4배 느림. 전환되면 로그에 남김 (2026-10-03 확정). 코드에서는 '주 서버/예비 서버'라고 부르고 주소는 `.env`에서 읽음 (2026-10-04)
- 원문 근거는 **문장 번호 방식**: 문장마다 번호(S1, S2…)를 붙여 AI에 보내고, AI는 컷마다 근거 문장 번호만 고름. 서버가 번호를 검사한 뒤 원문과 페이지를 DB에서 붙임. AI가 원문을 지어낼 수 없게 하기 위함 (2026-10-02)
