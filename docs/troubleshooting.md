## 1. 운영 장애 (AI 서버)

### 1-1. ⭐ AI 서버가 "살아 있다"고 답하면서 생성은 멎음 (gray failure)
- **증상:** 데스크탑(RTX 4060 Ti 8GB)으로 돌리자 핵심 사실 추출은 2분 만에 끝났는데(맥북 8분), 대본 쓰기 중에 진행률이 멈춤(39번은 첫 요청, 40번은 8/29). 오류 메시지 없음. 서버 상태 API는 "주 서버 사용 중, 정상".
- **원인:** 서버를 고를 때 `/api/version`("살아 있니?")만 물었다. 데스크탑 Ollama는 이 질문에는 답했지만 글 생성은 멎어 있었다. 짧은 질문을 직접 보내 보니 60초 동안 무응답. 모델(exaone 7.8B, 문맥 16384)이 7.1GB인데 GPU에 6.2GB만 올라가고 나머지가 CPU로 넘친 상태였다.
- **해결:** ① 대본 쓰기 모델의 문맥 길이를 따로 설정하고 16384 → 8192로 줄임(대화 기억 공간이 약 1GB 줄어 GPU 안에 들어가도록) ② 요청 제한 시간 10분 → 3분 ③ **서킷 브레이커:** 시간 초과가 난 서버는 5분간 건너뛰고 예비 서버를 씀.
- **배운 점:** "살아 있나(liveness)"와 "일을 받을 수 있나(readiness)"는 다른 질문이다. 감시 장치는 정상이라고 보는데 실제로는 장애인 상태를 **gray failure**라고 부른다. 이런 장애는 깔끔하게 죽는 장애(fail-stop)보다 잡기 어렵고, 결국 **제한 시간 + 반복 실패 시 차단**으로 막는다.
- **상태:** 문맥 8192로 줄여 모델이 GPU에 전부 들어간 뒤에도(5.7GB/5.7GB) 또 멎었다 → **메모리는 원인이 아니었다.** 실제 원인 추정은 1-8.

### 1-2. ⭐ 시간 초과가 연결 오류로 인식되지 않아 예비 서버로 안 넘어감
- **증상:** 40번 작업이 `Error while extracting response …`라는 알 수 없는 메시지로 실패. 예비 서버(맥북)가 살아 있었는데도 넘어가지 않았다.
- **원인:** 코드는 `ResourceAccessException`(연결 오류)일 때만 다음 서버로 넘기게 되어 있었다. 그런데 Spring `RestClient`는 **연결은 됐지만 답을 기다리다 시간이 초과되면** 일반 `RestClientException` 안에 `SocketTimeoutException`을 넣어 던진다. 결국 지금까지 예비 서버 전환은 "연결 거부"에만 동작하고 "시간 초과"에는 한 번도 동작하지 않았다.
- **해결:** 예외의 원인 사슬을 따라가 `IOException`이 있으면 연결 실패로 본다. HTTP 오류 응답(4xx·5xx)은 요청 내용 문제일 수 있어 넘기지 않는다.
- **발견 방법:** 3초 늦게 답하는 가짜 서버를 띄우고 제한 시간을 0.3초로 둔 테스트에서 드러났다. **실패 경로는 직접 재현해 보기 전까지 동작한다고 믿으면 안 된다.**

### 1-3. ⭐ 예비 서버가 재시작되는 순간 작업 전체가 실패
- **증상:** 49번 작업이 맥북으로 잘 돌다가 "주 서버와 예비 서버가 모두 응답하지 않습니다"로 실패.
- **원인:** 맥북 Ollama가 재시작되는 순간 요청이 끊겼다. 서킷 브레이커가 맥북도 5분간 건너뛰게 했고, 데스크탑은 이미 건너뛰는 중이라 남은 서버가 없었다. 몇 초 뒤면 돌아올 서버를 "멎은 서버"와 똑같이 취급한 것이 문제였다.
- **해결:** ① **실패 종류별 건너뛰기 시간:** 시간 초과(멎음)는 5분, 연결 끊김(재시작 중)은 10초 ② **재연결 대기:** 쓸 수 있는 서버가 없으면 바로 실패하지 않고 최대 1분 동안 몇 초 간격으로 다시 확인 ③ **수동 재연결 API** `POST /api/ai/reset`: 서버를 고친 뒤 건너뛰기를 바로 풂.
- **배운 점:** 재시도·차단 정책은 실패의 **종류**에 따라 달라야 한다. 일시적인 실패(transient)는 짧게 기다렸다 다시, 지속적인 실패는 오래 차단.

### 1-4. 진행률이 0/0으로 보여 멈춤과 대기를 구분할 수 없음
- **증상:** 대본 쓰기 단계에서 `0/0`이 계속 보여 "멈춘 건지, 첫 요청을 기다리는 건지" 알 수 없었다.
- **원인:** 전체 개수를 첫 AI 요청이 끝난 뒤에야 기록했다. 전체 개수는 시작 전에 이미 계산할 수 있었다.
- **해결:** 단계가 시작되자마자 `0/전체`를 기록한다.

### 1-5. 서버를 재시작하면 작업이 영원히 '처리 중'으로 남음
- **증상:** 멈춘 작업을 끝내려고 Spring을 재시작했더니 39번이 DB에 계속 `처리 중`으로 남았다.
- **원인:** 작업은 서버 안의 스레드가 돌리므로 서버가 꺼지면 함께 사라지는데, DB 기록은 아무도 고치지 않았다.
- **해결:** 서버가 시작될 때 '대기·처리 중' 작업을 찾아 "서버가 재시작되어 처리가 중단되었습니다"로 실패 처리(`StaleJobCleaner`).
- **배운 점:** 비동기 작업의 상태를 DB에 둘 때는 **프로세스가 죽었을 때의 정리**까지 설계해야 한다.

### 1-6. ⭐ 작업을 멈출 방법이 서버 재시작밖에 없음
- **증상:** 멈춘 작업을 끝내려면 Spring을 재시작해야 했고, 그러면 다른 작업까지 죽는다.
- **해결:** `POST /api/papers/{id}/cancel`. 상태 `CANCELLED`를 추가하고 **협력적 중단**으로 만들었다. 뒤에서 도는 처리는 AI 요청 하나가 끝날 때마다 진행률을 기록하는데, 이때 취소 여부도 확인해 스스로 멈춘다.
- **설계 포인트:**
  - 취소는 "대기·처리 중일 때만 취소로 바꾸는" **조건부 UPDATE 한 번**이다. 확인과 변경 사이에 틈이 없어(원자적) 끝난 작업을 취소하는 일이 없다.
  - 작업 테이블에 **`@Version`(낙관적 락)**을 달았다. 처리 쪽이 진행률을 저장하려는 순간 취소가 먼저 들어오면 처리 쪽 저장이 실패하고 "취소됨"으로 정리된다. **취소가 진행 기록을 덮어쓰지 못하게 하는 장치**다.
  - 스레드를 강제로 멈추는 방식(interrupt)은 쓰지 않았다. 지금 쓰는 HTTP 클라이언트는 응답을 기다리는 중에 interrupt에 반응하지 않기 때문이다. 그래서 진행 중인 AI 요청 하나는 끝까지 간다(최대 3분).
- **남은 일:** 취소 즉시 진행 중인 AI 요청까지 끊으려면 취소 가능한 HTTP 클라이언트(JDK `HttpClient`)로 바꿔야 한다.

### 1-7. 트레이에서 Ollama를 껐다 켜도 멎은 상태가 그대로
- **증상:** 데스크탑 Ollama를 "재시작했다"고 했는데 계속 무응답.
- **원인:** 트레이 아이콘의 종료는 앱만 끄고, 실제로 생성을 돌리는 하위 프로세스는 남은 것으로 보인다. 증거는 새로 켠 Ollama라면 비어 있어야 할 모델 목록(`/api/ps`)에 **40번 때 올라간 모델이 문맥 16384 그대로** 남아 있던 것.
- **해결:** PC 재부팅(진행 중).
- **배운 점:** "재시작했다"는 말 대신 **확인할 수 있는 지표**(모델 목록이 비었는지, 짧은 질문에 답하는지)로 검증한다.

### 1-8. ⭐ 끝나지 않는 생성 (데스크탑이 멎은 실제 원인, 확인됨)
- **증상:** 데스크탑은 qwen3(핵심 사실 추출)에서는 한 번도 멎지 않고, exaone(대본 쓰기)에서만 0~8번째 요청 사이 아무 데서나 멎었다. 멎으면 3토큰짜리 짧은 질문도 답하지 못했고, Spring이 연결을 끊은 뒤에도 10분 넘게 회복되지 않았다(81번: 05:35:41 시간 초과 → 5분 뒤 다시 써 보니 또 시간 초과). 같은 모델·같은 요청을 받은 맥북은 멎지 않았다.
- **확인한 것:** 데스크탑 `server.log`를 보면 Ollama 0.35.1이 생성 프로그램(`llama-server`)을 `-np 1`(생성 창구 1개), `--context-shift`(기억 공간이 차도 오래된 부분을 지우며 생성을 계속)로 띄운다. GPU 여유는 6.5GB, exaone 예상 5.4GB로 메모리는 충분했다.
- **원인:** 작은 모델이 JSON을 쓰다 같은 글자를 반복하는 고리에 빠지면, `--context-shift` 때문에 기억 공간이 차도 끝나지 않는다. 우리 요청에는 출력 길이 상한도 없었다. 창구가 하나라 다른 요청은 모두 그 뒤에서 기다린다.
- **확인(81번 다시 시도, 05:52):** 출력 상한을 넣자 데스크탑의 답이 **1500토큰 상한에 걸려 30초 만에 잘렸고**, 다시 묻자 Ollama가 스스로 `prediction aborted, token repeat limit reached`(500)를 돌려줬다. 반복 고리가 실제로 일어나고 있었다. 맥북 Ollama 설정도 같았고(`--context-shift`, 반복 억제 `repeat_penalty = 1.000` 즉 꺼짐), 맥북이 안 걸린 것은 운이었던 것으로 본다.
- **해결:** ① 모든 AI 요청에 **출력 길이 상한**(`num_predict` 1500토큰) ② 잘리거나 JSON이 깨진 답은 작업 실패 대신 **다시 묻기**(깨진 답은 대화에 넣지 않음, 모두 깨지면 이유를 밝혀 실패) ③ 상한에 걸린 답은 끝부분과 함께 **우리 로그에 기록** ④ Ollama의 "반복 한도 도달"(500)도 서버 고장이 아니라 깨진 답으로 보고 다시 묻기(처음엔 500을 요청 오류로 보고 작업을 실패시켰다) ⑤ **반복 억제** `repeat_penalty` 1.1 명시(Ollama 0.35의 기본값이 1.0, 즉 꺼져 있었다).
- **배운 점:** AI 출력 길이에는 **항상 상한을 둔다.** 외부 시스템이 "언젠가 끝나겠지"라는 가정은 설정 하나(`--context-shift`)로 깨진다. 모델 탓만 하기보다 **우리가 통제할 수 있는 쪽**(상한, 다시 묻기, 기록)을 고친다.

### 1-9. 실패한 작업을 되살릴 방법이 없음
- **증상:** 서버 재연결(`/api/ai/reset`)을 눌렀는데 실패한 50번 작업은 그대로였다.
- **원인:** reset은 "건너뛰기 표시"만 지운다. 작업이 **아직 살아 있을 때**(예비 서버로 느리게 도는 중) 빠른 주 서버로 바로 돌아오게 하는 기능이지, 이미 실패한 작업을 되살리지는 못한다. 실패한 작업을 다시 돌리는 기능이 빠져 있었다.
- **해결:** `POST /api/papers/{id}/retry` — 실패·취소된 작업을 **DB에 저장된 문장으로 핵심 사실 추출부터** 다시 돌린다(PDF를 다시 올리거나 GROBID를 다시 돌리지 않음). "실패·취소일 때만 대기로"를 조건부 UPDATE 한 번으로 해서 두 번 눌러도 한 번만 시작된다. 상태 변경을 먼저 커밋한 뒤 비동기 처리를 시작한다(커밋 전에 시작하면 처리 쪽이 옛 상태를 읽는다).
- **남은 일:** 멈춘 곳부터 이어서 하기(예: 대본 쓰기 5/30부터)는 핵심 사실 설계도와 쓰다 만 컷을 DB에 저장해야 해서 다음으로 미룸.
- **해결(2026-10-20):** 핵심 사실 추출이 끝나면 설계도를 `paper_job.plan_json`(Flyway V2)에 저장하고, 다시 시도할 때 설계도가 있으면 **대본 쓰기부터** 한다. 194번: 대본 쓰기 3/33에서 취소 → 다시 시도 1분 41초 만에 완료, 사실 추출 단계를 건너뜀. 쓰다 만 컷까지 이어 쓰지는 않는다(대본 쓰기는 처음부터). 설계도 모양(`ComicPlan`)이 바뀌어 예전 JSON을 읽지 못하면 사실 추출부터 다시 한다.


### 1-10. 데스크탑 그래픽카드 오류로 작업 실패 (175번, 원인 미확인)
- **증상:** 사실 모델을 Gemma 4로 바꾼 첫 실행에서, 대본 쓰기 2쪽 중 Ollama가 `500 … CUDA error: an illegal memory access was encountered`를 돌려주고 작업이 실패했다.
- **확인한 것:** 직후 두 모델 모두 정상 응답했고, `retry`로 다시 돌리니 끝까지 완료됐다. 데스크탑 Ollama는 gemma4:e4b의 크기를 0.26GB로 잘못 보고하지만, 모델을 번갈아 불러 보니 앞 모델은 제대로 내려갔다 — "두 모델이 함께 올라가 메모리가 넘쳤다"는 가설은 확인되지 않음.
- **지금 동작:** 이런 500 오류는 연결 오류가 아니라서 예비 서버로 넘기지 않고 작업이 바로 실패한다. 실패한 작업은 `retry`로 살릴 수 있다(1-9).
- **다음에 날 때:** 그 시각의 데스크탑 Ollama 로그(`%LOCALAPPDATA%\Ollama\server.log`)를 본다. 자주 나면 이 오류를 '다시 묻기' 대상으로 넣을지 검토.
- **두 번째 발생(183번, 2026-10-06 00:47):** 175번 1차와 같은 논문(latent diffusion), 같은 단계(대본 쓰기 2쪽, exaone)에서 같은 오류. 줄 세우기 시험 중이었고 앞의 두 작업은 정상 완료. 시험 서버로 돌린 177·179번(같은 논문)은 문제없었다 — 원인은 여전히 미확인. 같은 자리에서 두 번 났으므로 '다시 묻기' 대상에 넣는 것을 검토할 때가 됐다.

### 1-11. ⭐ 작업이 무제한으로 동시에 돌아 AI 서버 하나를 서로 붙잡음 (벌크헤드)
- **증상:** 39·40번을 함께 돌리자 둘 다 멈췄다. 1-8(끝나지 않는 생성)과 별개로, 여러 작업이 동시에 AI 서버를 쓰면 요청이 순서를 기다리다 3분 시간 초과 → '서버 고장'으로 보고 예비 서버(맥북)로 넘어가 더 느려지는 연쇄가 생길 수 있었다.
- **원인:** `@Async`가 Spring 기본 실행기(담당자 최대 8명, 대기 줄 무제한)를 썼다. AI 서버는 동시에 하나만 답을 만든다.
- **해결:** 논문 처리 전용 실행기 `jobExecutor`(담당자 1명, 대기 줄 5개). 넘치면 429로 거절하고, 대기 중인 작업은 상태 조회에서 지금 순번(`queuePosition`)을 보여 준다. 순번은 DB에서 '나보다 먼저 줄 선 대기 작업 수 + 1'로 세서 다시 시도·취소·재시작에도 맞다. 대기 작업마다 PDF(최대 50MB)를 메모리에 들고 있어 대기 줄을 5로 묶었다(최대 250MB).
- **배운 점:** 공유 자원(AI 서버 1대)의 용량에 맞춰 동시 실행 수를 묶어야 한다. 기본 설정은 '무제한'인 경우가 많다.

> **운영체제 개념과 비교:** 처음에는 데드락처럼 보였지만 데드락은 아니다. 데드락의 네 조건(상호 배제·점유 대기·비선점·순환 대기) 중 **순환 대기**가 없다. Spring은 Ollama를 기다렸지만 Ollama는 Spring의 무엇도 기다리지 않았다. 실제로 해당하는 개념은 **무한 대기(타임아웃 부재)**, **head-of-line blocking**(Ollama 생성 슬롯 1개를 멎은 요청이 차지), **half-open 연결**, 그리고 해법인 **서킷 브레이커·벌크헤드**(Nygard, *Release It!*)다.

## 2. Spring · DB

### 2-1. ⭐ enum에 새 값을 추가했더니 DB가 거부함
- **증상:** 작업 상태에 `CANCELLED`를 추가하자 저장할 때 `violates check constraint "paper_job_status_check"`.
- **원인:** Hibernate는 테이블을 처음 만들 때 enum 칸에 허용 값 검사(CHECK)를 붙인다. `ddl-auto=update`는 새 칸은 추가하지만 **이미 있는 검사는 고치지 않는다.**
- **해결:** 검사를 다시 만드는 SQL을 한 번 직접 실행했다(`backend/src/main/resources/db/manual/2026-10-05_job_status_cancelled.sql`).
- **배운 점:** `ddl-auto=update`는 개발 초기용이다. 실제 운영 DB의 구조 변경은 **Flyway 같은 마이그레이션 도구**로 버전 관리해야 한다.
- **근본 해결(2026-10-20, Flyway):** 지금 DB 구조를 `pg_dump --schema-only`로 떠서 `V1__init.sql`로 만들고(Hibernate가 지은 제약 이름까지 그대로 — 기존 DB와 새 DB의 이름이 같아야 다음 SQL 파일이 양쪽에서 똑같이 돈다), Hibernate는 `ddl-auto=validate`(검사만)로 바꿨다. 이미 표가 있는 DB는 `baseline-on-migrate`로 V1을 실행하지 않고 '1번까지 끝남'만 기록한다. 다음 변경(V2, 설계도 칸)은 서버가 켜질 때 자동으로 적용됐다. 빈 DB(테스트용 일회용 DB)에 V1·V2가 차례로 돌고 엔티티 검사를 통과하는지 `MigrationTest`로 확인한다. 적용 전에 DB를 백업했다(논문 원문이 들어 있어 저장소 밖에 보관).

### 2-8. ⭐ 테스트가 실제 서비스 DB를 같이 씀 (작업을 실패로 바꿀 뻔함, 실제 번호가 사라짐)
- **증상:** 서버 재시작 시 '처리 중' 작업을 정리하는 기능을 넣은 뒤, 테스트 로그에 "중단된 작업 2개를 실패로 표시했습니다"가 찍혔다.
- **원인:** 테스트는 개발 서버와 **같은 DB**를 쓰고, 테스트용 Spring이 뜰 때도 정리 기능이 돈다. 이번에 정리된 건 테스트가 잠깐 만든 가짜 작업이라 피해는 없었지만, 서버가 작업을 돌리는 중에 테스트를 실행하면 **그 작업을 실패로 바꿔 버린다.** 테스트 로그도 서버 로그 파일에 섞였다.
- **임시 해결:** 테스트 실행 때는 정리 기능을 끄고, 테스트 로그는 `build/test-logs/`로 분리.
- **같은 원인의 다른 증상:** 만화 번호가 11, 24, 69, 86처럼 띄엄띄엄이었다. 테스트가 가짜 만화를 만들고 되돌릴 때 **번호 발급기(시퀀스)는 되돌리지 않아서** 실제 서비스 번호가 테스트 한 번에 몇 개씩 사라졌다.
- **근본 해결(Testcontainers):** 테스트마다 Docker로 **일회용 PostgreSQL 17**을 띄워 쓰고 끝나면 지운다(`TestcontainersConfiguration`, `@ServiceConnection`, 테스트 6개 클래스에 `@Import`). 테스트는 `.env` 없이 돌고 실제 AI 서버 주소도 쓰지 않는다. 임시 설정(정리 기능 끄기)은 지웠다. **증명:** 테스트 전후로 실제 DB의 번호 발급기가 그대로(작업 172, 문장 4300, 만화 86, 컷 296)였고, 테스트 중 `127.0.0.1`에만 열린 테스트 DB가 떴다가 끝나고 바로 사라졌다.
- **보안 검토에서 걸린 것:** Testcontainers는 기본으로 Docker에 "빈 포트에 열어 달라"고만 해서 **모든 네트워크(0.0.0.0)**에 열린다. 테스트 DB는 코드로 `127.0.0.1`에 묶었지만, 함께 뜨는 청소부 컨테이너(Ryuk)는 묶을 수 없어 테스트 동안 0.0.0.0에 열렸다. Docker 전체 기본값을 127.0.0.1로 바꾸는 방법은 다른 프로젝트(다른 기기에서 접속, `localhost`가 IPv6로 가는 경우)에 영향이 있어서, **이 프로젝트 테스트에서만 Ryuk를 껐다**(`TESTCONTAINERS_RYUK_DISABLED`). 대신 테스트를 강제 종료하면 테스트 DB가 남을 수 있다(`docker rm -f`로 정리).
- **배운 점:** 테스트와 실제 서비스는 **DB부터 분리**한다. 그리고 새 도구를 넣을 때는 "기본값이 어디에 열리는가"를 꼭 확인한다 — 내가 직접 띄운 것만 안전하게 설정해도, 도구가 대신 띄우는 것은 기본값을 따른다.

### 2-2. ⭐ 기존 행이 있는 테이블에 빈 값 불가 칸을 추가하지 못함
- **증상:** 진행률 칸(`progress_done`, `int`)을 추가했더니 칸이 생기지 않고 테스트가 실패.
- **원인:** `int`는 빈 값(null)이 될 수 없는데, 이미 있는 작업 행들에 넣을 값이 없었다.
- **해결:** `@ColumnDefault("0")`로 기본값을 줬다. 나중에 `@Version` 칸을 추가할 때도 같은 방법을 썼다.

### 2-3. ⭐ Java 텍스트 블록이 줄 끝 공백을 지워 AI 지시문이 붙어 버림
- **증상:** AI에게 보내는 규칙이 "…섞지 않는다.영어 용어는…"처럼 띄어쓰기 없이 붙었다.
- **원인:** Java의 여러 줄 문자열(텍스트 블록, `"""`)은 **각 줄 끝의 공백을 자동으로 지운다.** 줄 끝 공백에 기대어 다음 문자열과 이어 붙이고 있었다.
- **해결:** 공백을 텍스트 블록 밖에서 붙이고(`""" + " " + 규칙`), 지시문에 공백이 들어가는지 확인하는 테스트를 추가했다.

### 2-4. AI에게 넘긴 대화 목록이 나중에 바뀜
- **증상:** 테스트에서 가짜 AI가 받은 대화 기록이 실제로 보낸 것과 달랐다.
- **원인:** 다시 쓰기 요청을 덧붙이는 목록을 그대로 넘겨서, 넘긴 뒤에 내용이 바뀌었다(같은 목록을 두 곳이 공유, aliasing).
- **해결:** 바뀌지 않는 복사본(`List.copyOf`)을 넘긴다.

### 2-5. 생성자가 둘이 되자 Spring이 객체를 못 만듦
- **증상:** 테스트에서 시간을 조작하려고 생성자를 하나 더 만들었더니 서버 시작 시 `No default constructor found`.
- **원인:** 생성자가 둘이면 Spring은 어느 것을 쓸지 모른다.
- **해결:** 쓸 생성자에 `@Autowired`를 붙였다.

### 2-6. 작업 번호가 건너뜀 (3번 없음)
- **증상:** 작업 번호가 1, 2, 4로 이어졌다.
- **원인:** 테스트가 저장했다가 되돌린(롤백) 작업도 번호를 하나 썼다. DB의 번호 발급기(시퀀스)는 롤백되지 않는다. 정상 동작이다.

### 2-7. 결과 파일을 옮겼더니 시험 스크립트가 입력 파일을 못 찾음
- **증상:** 결과 폴더를 정리하면서 `spring-result.json`을 옮겼는데, 시험 스크립트 3개가 이 파일을 **입력**으로 읽고 있었다.
- **원인:** 옮기기 전에 출력 경로만 확인하고 입력 경로는 확인하지 않았다.
- **해결:** 스크립트의 입력 경로를 새 위치로 고쳤다.
- **배운 점:** 파일을 옮길 때는 그 파일을 **읽는 곳과 쓰는 곳 모두** 검색한다.

### 2-9. ⭐ 만화 하나 조회에 DB 질의 71번 (N+1)
- **증상:** 만화 조회(`GET /api/papers/{id}/comic`)가 만화 → 쪽 → 컷 → 대사·근거를 필요할 때마다 하나씩 읽어(지연 로딩), 4쪽 32컷 만화 하나에 질의가 71번(작업 1 + 만화 1 + 쪽 1 + 쪽마다 컷 4 + 컷마다 대사 32 + 컷마다 근거 32) 나갔다.
- **측정:** `ComicQueryTest`가 Hibernate Statistics로 조회 한 번의 질의 수를 센다. 고치기 전 71번으로 실패(10번 이하 기준).
- **해결(사용자가 직접):** `spring.jpa.properties.hibernate.default_batch_fetch_size=100` 한 줄. 지연 로딩할 때 같은 종류를 최대 100개씩 `IN (…)`으로 묶어 읽는다 → **6번**.
- **fetch join을 안 쓴 이유:** 컷 아래에 목록이 두 개(대사, 근거)라 한 번에 붙여 가져오면 Hibernate가 `MultipleBagFetchException`을 낸다. 묶어 읽기는 코드 변경 없이 모든 지연 로딩에 적용된다.

### 2-10. ⭐ 오류 설명이 버려지고, 파일 없이 업로드하면 500
- **증상:** 서비스가 "작업을 찾을 수 없습니다: 999"처럼 설명을 붙여 던져도 응답은 `{"status":404,"error":"Not Found"}`뿐이었다(Spring Boot 기본 오류 응답은 설명을 숨김). 파일 없이 `POST /api/papers`를 보내면 요청 잘못인데 500(서버 고장)이 나왔다. PDF가 아닌 파일도 작업을 만든 뒤 GROBID 단계에서야 실패했다.
- **해결:** `GlobalExceptionHandler`(@RestControllerAdvice)로 모든 오류를 RFC 9457 Problem Details 한 가지 모양으로 통일했다. 404·409는 부모 클래스(ResponseEntityExceptionHandler)가 설명을 그대로 싣고, 형식이 틀린 값은 400 + 어느 값인지, multipart가 아닌 업로드는 400, 예상 못 한 오류는 500 + 일반 안내만 준다(예외 메시지에 섞일 수 있는 DB 주소·설정값은 로그에만). 업로드 입구에서 파일 맨 앞의 `%PDF-`로 PDF인지 확인한다(이름·Content-Type은 보내는 쪽이 바꿀 수 있다).
- **확인:** `ApiErrorTest`(Controller만 띄우는 @WebMvcTest, 서비스는 가짜) 7개, 재시작한 서버에 실제 요청 6가지.

### 3-10. ⭐ 자동 검사는 "0건"인데 직접 읽어 보니 문제가 있음 (81번)
- **증상:** 81번 결과를 자동 검사로 보면 장면 칸 혼입·흐름 칸 이름표·해설 말투가 모두 0이었는데, 대본을 처음부터 읽어 보니 문제가 여럿 있었다.
  - 장면 칸에 따옴표 대사가 통째로 들어감(`질문한다: "박사님, …"`), 앞뒤에 `br/` 찌꺼기, 끝에 `: `
  - 사실 컷 하나와 연출 컷 둘에 대사가 하나도 없음(대사가 장면 칸으로 들어가고, 정리 단계에서 빈 대사가 빠짐)
  - 대사 앞에 `- `, `-- `, 대사 속 괄호 행동 설명 `(눈을 반짝이며)`
  - 논문에 없는 용어("커널 필터링")를 이야기 뼈대가 지어내 연출 컷 해설과 장면에 번짐
  - 사실 덧붙임("음성 같은 입력", "SR3는 세부 질감이 선명")
- **원인:** 검사 규칙은 **지금까지 본 실수의 모양**(`누리:` 이름표, `*`, `{`)만 잡는다. 모델은 다른 모양(따옴표, `br/`, `-`)으로 같은 실수를 한다. 이야기 뼈대와 연출 컷은 사실 검사 대상이 아니었다.
- **해결(보강 3차):** ① 장면 칸 검사에 큰따옴표·쌍점·`br/`를 추가하고, 정리할 때는 섞인 곳 앞의 **끝난 문장까지만** 남김 ② 대사가 하나도 없으면 다시 쓰기 ③ 대사 속 괄호 행동 설명은 문제로 알리고 지움, 대사 앞 `-`·끝 쉼표는 정리 ④ 이야기 뼈대·연출 컷에 "다룰 내용에 나온 용어만, 연출 해설은 상황과 감정만" 규칙 ⑤ 이야기 뼈대·연출 컷의 **영어 낱말이 논문 원문에 없으면** 다시 쓰기 ⑥ 조각 제목을 로그에 남겨, 지어낸 용어가 어디서(조각 제목인지 이야기 뼈대인지) 생겼는지 추적. 새 규칙을 13·23·81번에 적용해 보면 잡히는 것은 모두 실제 문제였다(81번: 장면 4컷, 대사 없는 컷 3개, 괄호 행동 1개).
- **추가 해결(용어에 영어 원문 붙이기, 사용자 제안):** 논문을 확인해 보니 `filtering`은 0번, `kernel`은 부록에 다른 뜻으로 1번, 실제 용어 `convolutional`은 8번 나왔다. "커널 필터링"은 옮긴 말이 아니라 지어낸 말이었다. 그래서 핵심 사실·조각 제목·이야기 뼈대에서 기술 용어는 **"한국어(논문 영어 원문)"**으로 쓰게 하고(예: 컨볼루션 샘플링(convolutional sampling)), 괄호 안 영어가 논문(문장·섹션 이름·제목)에 없으면 다시 쓰게, 끝까지 남은 사실은 버리게 했다. 사실 컷 대사는 괄호를 강제하지 않고(대사가 딱딱해짐) 영어를 쓰면 논문 낱말인지만 본다. 복수형은 같은 낱말로 본다(논문 'GANs', 대본 'GAN'). 81번 결과 전체에 적용해 오탐 0건.
- **한계:** AI가 괄호 없이 **한국어로만** 지어내면 여전히 코드로 잡지 못한다(규칙과 로그 추적에 맡김). 대사의 사실 덧붙임("음성 같은 입력")도 코드로 잡기 어려워 **사람 검수 항목**으로 남긴다.
- **배운 점:** 자동 지표가 좋아졌다고 품질이 좋아진 것은 아니다. **결과를 사람이 처음부터 읽는 검수**를 함께 해야 하고, 거기서 찾은 실수를 다시 검사 규칙으로 옮긴다(이 과정을 반복).

### 3-12. ⭐ 형식이 좋아지자 드러난 사실 정확도 문제 (172번)
- **증상:** 사실 25개 중 5개가 틀림. 표 제목만으로 실험을 지어냄(181, 13번에 이어 재발), 논문 추출 때 위첨자가 사라진 "256 2"(원래 256²)를 "256x2"로 씀, 비교 대상을 바꿈(228: 픽셀 vs 잠재 확산 → LaMa와 비교), 문장에 없는 결과를 지어냄(207: "사용자 조사를 했다" → "선호도가 높았다"), "GAN보다 우수" 덧붙임. 용어 "한국어(영어 원문)" 규칙은 qwen3가 따르지 않아 사실에 괄호가 하나도 없었다.
- **원인:** 사실 고르기(qwen3) 결과를 **근거 문장과 대조하는 단계가 없다.** 지금 검사는 번호·섞인 단어·수식·인용 같은 형식만 본다.
- **해결 1 — 표·그림 제목 빼기:** "Table 2. Evaluation of …", "Comparison of …"로 시작하는 제목 문장은 근거 후보로 보여 주지 않는다. 처음 만든 규칙(`Tab.`·`Fig.`로 시작)은 "Tab. 8 shows …", "Tab. 2. We note that …"처럼 **표를 인용하는 본문 문장까지** 20개를 잡아서, 실제 논문 383문장으로 오탐을 보며 좁혔다(최종 4개, 모두 진짜 제목). 사실 끝의 `(239)` 같은 번호도 지우고, 남아 있으면 다시 쓰게 했다.
- **해결 2 — 사실 확인 단계:** 사실을 고른 뒤 같은 모델(qwen3)에게 "이 사실이 근거 문장과 어긋나나?"를 한 번 더 묻고(조각마다 1번), '틀림'이면 이유를 알려 주며 다시 쓰게, 다시 써도 '틀림'이면 버린다. 확인이 깨지면 작업을 멈추지 않고 건너뛴다. 172번 실제 사실 25개로 데스크탑에서 미리 재 봤다.

  | 방식 | 걸린 시간 | 알려진 틀린 사실 4개 중 | 맞는 사실을 틀림으로 |
  | --- | --- | --- | --- |
  | 참·거짓 두 단계 | 40초 | 4개 | **15개 거부** (240번 한계 같은 맞는 사실까지) |
  | **맞음·과장·틀림 세 단계 + 섹션 이름 + 실패 사례 예시 (채택)** | **30초** | 2개 | 4개 (다시 보니 모두 작은 흠이 있었음: 이름 붙이기, 번역 어긋남, 과장, 잘린 근거) |
  | 세 단계 + 생각하기 켬 | 388초 | 4개 | 8개 |

  세 단계 방식은 세 번 돌려도 같은 6개를 짚어 안정적이었다. 놓친 것: "GAN보다" 덧붙임(1-7). 표 제목에서 지어낸 사실(3-6)은 해결 1로 생기지 않는다. "256x2"(원문 자체가 "256 2")는 원문을 고쳐야 해서 못 잡는다.
- **실제 실행(173번, 172번과 같은 논문):** 6분 53초(+2초 — 확인에 51초 더 들었지만 사실이 25개 → 22개로 줄어 대본 쓰기가 40초 빨라짐). 명백히 틀린 사실이 5개 → 2개로 줄었다. 표 제목 지어내기, 사용자 조사 결과 지어내기, "GAN보다" 덧붙임, `(239)` 번호는 사라졌다. 확인 단계가 버린 3개 중 1개는 **잘못 버렸다**: 근거가 "…over that of [88]"처럼 인용 번호로만 비교 대상을 가리키는데, [88]이 LaMa라는 것을 AI가 알 수 없었다. 남은 문제: [228] 비교 대상 바꾸기(172번과 같은 실수 재발), 관련 연구를 "이 연구는"으로 바꾸기, "stagnating"을 "안정화되지 않는다"로 옮기기.
- **배운 점:** 같은 작은 모델로 자기 결과를 검증하면 **엄격하게 할수록 맞는 것까지 버린다**(정밀도와 재현율의 줄다리기). 판정 단계를 세분하고 '틀림'만 처리하는 것이 실용적인 타협이었다. 실제 데이터로 **먼저 재 보고** 넣은 것이 중요했다 — 처음 버전을 그대로 넣었다면 맞는 사실이 절반 넘게 사라졌을 것이다.
- **배운 점:** 겉모습(형식)을 고치면 속(내용) 문제가 보인다. 학습 만화에서는 **사실 정확도가 형식보다 우선**이다.

**배운 점:** 작은 모델(7~8B)에게는 지시를 잘 지키라고 부탁하기보다 **구조로 실수할 수 없게 만드는 것**(하나씩 요청, 코드가 근거·해설을 붙임, 이름 칸)이 효과가 크다. 검사는 특정 실수 하나가 아니라 **실수의 종류**를 잡아야 한다.

- **고친 것(2026-10-05):** 지시문 예시를 일반 용어로 바꾸고 이야기 설정 예시는 지움, 사실이 한 섹션에서만 나오면 다른 섹션의 결과 문장(비교·변화 낱말 + 숫자) 번호를 알려 주며 다시 고르게 함, 쪽당 사실 6개 상한과 한계 조각 보너스는 마지막 쪽에만.
- **결과(177·178번):** '고화질' 사라짐, 두 번째 논문 핵심 결과 들어감, 모든 쪽 8컷 이하, 틀린 사실 두 논문 모두 0개. 그런데 **새로 넣은 용어 예시 '표본 크기(sample size), 기준 모델(baseline)'이 178번 이야기 흐름에 그대로 들어갔다** — 구체적인 예시 낱말은 무엇으로 바꿔도 새어 나올 수 있다. 예시는 형식만 보여 주는 쪽이 낫다.
- **배운 점:** 한 데이터로만 고치면 그 데이터에 맞춰진다(과적합). 시험 자료를 하나 더 두는 것만으로 사실 정확도(일반화됨)와 사실 고르기·이야기(맞춰짐)가 갈렸다. 지시문 예시는 특정 논문 주제와 무관하게 써야 한다.

### 3-15. 용어를 통일했더니 어색한 번역이 통일돼 퍼짐 (179·180번)

- **증상:** 같은 용어를 조각마다 따로 옮겨 data comics가 "데이터 만화"·"데이터 코믹스"로 섞였다(176·178번).
- **해결:** 사실을 뽑기 전에 초록에서 핵심 용어 8개까지 골라 번역을 하나로 정하는 '용어 정하기' 단계를 넣고, 정한 번역을 모든 지시문에 붙이고, '쓰지 않을 다른 번역'을 쓰면 다시 쓰게 했다. 결과 "데이터 코믹스" 0회.
- **새로 생긴 문제:** 무엇으로 통일할지를 작은 모델이 정하니, 어색한 번역이 정해지면 그대로 만화 전체에 퍼졌다("잠재 확산 모델"이 금지되고 "잠재 공간 확산 모델" 29회, "글자로 그림 만들기", "흥미 유발을 느낀다"). 괄호에 영어 대신 한국어를 넣는 실수도 생겼다("윤리적 문제(윤리적 문제)"). 다시 쓰기가 늘어 7~15% 느려졌다.
- **추가 조치:** 괄호 안에 한국어만 있으면(숫자·기호 없는 한글 낱말만) 사실·이야기 뼈대를 다시 쓰게 했다. '무엇으로 통일할지'의 품질은 손보지 않고 두기로 함 — AI 요약은 어떻게 해도 완벽할 수 없다는 판단(사용자 결정, 2026-10-05).
- **배운 점:** 일관성과 품질은 다른 문제다. 통일 장치는 '무엇으로 통일하느냐'의 품질을 함께 관리해야 한다.
- **함께 고친 것:** 용어 규칙 예시를 낱말 없이 형식만 남겼더니(178번의 '표본 크기(sample size)' 새어 나옴) 예시 낱말 0회. 흐름 칸의 `>`·`$` 정리.

### 3-16. 대본 모델 비교: exaone3.5 ↔ gemma4 (179·180번 ↔ 184·185번)

- **배경:** exaone3.5는 연구 목적 전용 라이선스라 배포할 수 없다. 이미 사실 추출에 쓰는 gemma4(Apache 2.0)로 대본도 쓸 수 있는지 비교했다.
- **결과(1회씩):** 대본 쓰기 404·369초 → 61·63초(약 6배), 작업 전체 7분대 → 2분대. 누리 존댓말 어김 5·1 → 0·0, 80자 넘는 대사 5·3 → 0·0. exaone은 묘사가 풍부하지만 장황하고 반복되며, gemma는 간결하고 규칙을 잘 지키지만 사실과 안 맞는 비유가 가끔 나온다.
- **배운 점:** "한국어 특화 모델이 한국어 글을 더 잘 쓴다"는 기대와 달리, 규칙 준수·속도·라이선스까지 보면 범용 모델이 나을 수 있다. 모델 선택은 품질 하나가 아니라 라이선스·속도·운영(그래픽카드 메모리) 기준을 함께 본다.

### 3-17. ⭐ 대본이 '묻고 답하기'의 나열이라 이야기가 이어지지 않음 (186번, 사용자 지적)
- **증상:** Gemini로 그림까지 그려 보니 정보 전달만 있고 이어지는 느낌이 없었다. 186번 사실 컷 22개 중 20개가 "박사님, …인가요?"로 시작하는 질문, 박사님 답 13개가 "응/맞아"로 시작. 1쪽에서 "반복 신경망은 안 쓴다" 다음 컷에 "반복 신경망이 중요한가요?"처럼 앞뒤가 거꾸로였다.
- **원인:** ① 사실 컷을 하나씩 따로 쓰고 앞 컷의 장면만 넘겨(예전에 대사를 넘기자 앞 내용을 끌고 와서 막았다) AI가 매번 새 질문으로 시작 ② 사실이 논문 순서(초록 → 서론)라 이야기 논리와 어긋남 ③ 줄거리가 쪽당 한 줄뿐 ④ 해설이 매 컷 사실 문장을 읽어 교과서 느낌.
- **해결:** 쪽마다 콘티(사실 컷의 순서 + 컷마다 '일어나는 일과 앞 컷과의 고리' 한 줄)를 먼저 짜고, 컷은 그 줄거리와 바로 앞 대사 한 줄을 받아 이어서 쓴다. 같은 모양의 질문이 연달아 나오면 다시 쓰게 한다. 사실 문장과 근거는 지금처럼 코드가 붙여 환각 방지는 그대로. 쪽 전체를 한 번에 쓰는 방식은 예전에 사실을 '비유'로 바꿔 근거를 피한 전례가 있어 택하지 않았다.
- **캐릭터:** 사용자는 치이카와·하치와레를 원했지만 작가의 저작권·상표 캐릭터라 공개 포트폴리오에 쓰면 위험 소지가 있어, 같은 귀여운 느낌의 오리지널 캐릭터 콩이(흰 햄스터)·냥박사(안경 쓴 고양이)로 바꿨다. 화자 이름은 `Speaker` 한 곳에서 가져오게 정리.

### 3-18. 그림 속 예시 문장을 논문 주장으로 씀 (186·187번)
- **증상:** 4쪽 사실 컷이 "The Law will never be perfect…"(법은 결코 완벽하지 않다)를 논문 내용처럼 말했다. 187번은 이 문장에서 "문제는 모델이 아니라 적용"이라는 이야기 결론까지 끌어냈다.
- **원인:** 이 문장은 논문 끝 부록의 주의 시각화 그림(Attention Visualizations)에 들어간 **입력 예시 문장**이다. 부록 검사는 "A. …", "B.1 …"처럼 알파벳 번호가 붙은 제목만 부록으로 보는데, 이 부록은 결론 뒤에 번호 없이 붙어 있어 본문으로 읽혔다.
- **해결:** 결론 섹션 다음에 한계·향후 연구가 아닌 섹션이 오면 거기서 본문을 끝낸다(`ChunkSplitter`). 188번: 본문이 Conclusion(192번 문장)에서 끝나고 그 문장 0개. 결론 뒤 "Limitations"는 그대로 남는지 테스트로 확인.

### 3-19. 같은 결과를 초록과 실험에서 두 번 말함 (187번)
- **증상:** "BLEU 28.4로 최고 성능"이 1쪽(초록, 근거 5번 문장)과 3쪽(실험, 근거 154번 문장)에 두 번 나왔다. 1쪽(기)에서 결과를 미리 말해 기승전결도 어긋났다.
- **원인:** 조각마다 따로 사실을 뽑는데, 초록·서론·결론은 실험 결과를 요약해 되풀이한다. 근거 문장이 달라 기존 중복 검사(같은 근거)에 걸리지 않았다.
- **해결:** 같은 결과 숫자(28.4, 12% 같은)를 담고 글자 유사도가 0.2 이상인 사실 쌍은 **요약 섹션(초록·서론·결론) 쪽을 버린다**(둘 다 같으면 뒤의 것). 188번 로그 "같은 결과를 말하는 사실을 버렸습니다", 실험 절 한 번만 남음. 0.2는 낮아 보이지만 숫자가 같아야 하는 조건과 함께라서, 같은 0.1을 쓰는 다른 사실(드롭아웃 0.1, 레이블 스무딩 0.1)은 남는 것을 테스트로 확인했다.

### 3-20. ⭐ 고칠 때마다 새 부작용: 쪽이 바뀔 때 이어 쓰기 (188~191번)
- **증상(188번):** 쪽을 여는 컷마다 같은 불평을 되풀이했다. 1·2·3쪽 첫 컷이 모두 "긴 문장은 왜 자꾸 틀리게 번역되는 걸까요?"
- **원인:** 쪽마다 따로 쓰면서 앞 쪽에서 무슨 일이 있었는지 넘기지 않았다. AI는 매 쪽 이야기 뼈대의 '문제'에서 다시 시작했다.
- **1차 해결 → 부작용(189번):** 앞 쪽 마지막 장면·대사와 이번 쪽 첫 사실 컷을 여는 컷에 넘겼다. 불평 되풀이는 사라졌지만, 여는 컷이 첫 사실 컷 장면을 **그대로 베꼈다**.
  > 1쪽 1컷(여는 컷) 콩이가 책상 앞에 앉아 노트북 화면을 응시하고 있다. 콩이의 표정은 답답해 보이며, 손가락으로 키보드를 두드리고 있다.
  >
  > 1쪽 2컷(첫 사실 컷) 책상 앞에 앉아 노트북 화면을 응시하는 콩이. 표정은 답답해 보이며, 손가락으로 키보드를 두드리고 있다.

  장면 유사도가 1쪽 0.81, 3쪽 1.00, 4쪽 0.95였다(187·188번은 0.43 이하).
- **2차 해결 → 부작용(190번):** 장면 0.5·대사 0.4 이상 겹치면 여는 컷을 다시 쓰게 했다(190번 장면 0.16~0.39). 그러자 이번에는 첫 사실 컷이 앞 쪽 마지막 대사를 **그대로 옮겼다**.
  > 1쪽 8컷(닫는 컷) 콩이: 다른 방법으로는 이 문장을 어떻게 이해할 수 있을까요?
  >
  > 2쪽 2컷(첫 사실 컷) 콩이: 다른 방법으로는 이 문장을 어떻게 이해할 수 있을까요?

  '같은 대사' 검사는 쪽마다 따로 세서 쪽 경계를 넘는 복사를 못 봤다.
- **3차 해결(191번):** 사실 컷 대사가 바로 앞 대사(앞 쪽에서 넘어온 것 포함)와 0.4 이상 겹치면 다시 쓰게 했다. 191번 베낀 대사 0. 기준값은 187~190번 실제 대사로 쟀다 — 이웃한 컷끼리의 대사 유사도는 베낀 경우(0.48)를 빼면 0.34 이하였다.
- **왜 부작용이 매번 나왔나:** AI에게 새로 넘긴 글은 **그대로 베낄 재료**가 된다. 작은 모델은 "이어서 써라"를 "비슷하게 써라"로 받아들이기 쉽다. 그래서 넘기는 정보를 늘릴 때마다 그 정보를 베꼈는지 보는 검사가 함께 필요했다.
- **배운 점:** AI에게 맥락을 더 줄 때는 **"베꼈는지" 검사를 같이 넣는다.** 그리고 한 번에 하나만 바꾸고 실제로 돌려 읽어 봐야 부작용이 어느 수정에서 왔는지 말할 수 있다. 검사 기준값은 감으로 정하지 않고 지금까지의 실제 결과로 잰다.
- **남은 한계:** 글자는 다르지만 같은 생각을 두 번 말하는 것(190번 4쪽: "번역 외에 다른 언어 작업에도 이 방법이 적용될 수 있을까요?" → "트랜스포머가 번역 말고 다른 일도 잘할 수 있는지 실험해 봐야겠어요!", 유사도 0.06)은 글자 유사도로는 잡지 못한다.

### 3-21. ⭐ 비유와 대사가 사실과 반대로 감 → 대사 사실 확인 단계 (188~191번)
- **증상(188번):** 해설(사실 문장)은 맞는데, 그 옆 대사가 사실과 어긋났다.
  > 사실: 학습률은 처음에 선형적으로 늘리고, 그 다음부터는 스텝 수 역제곱근에 비례해 줄였다.
  >
  > 냥박사: 마치 달리기를 시작할 때 천천히 몸을 풀다가 **점점 속도를 올리는** 것과 비슷하다고 보면 돼.

  > 사실: 영어→독일어 번역에서 이전 최고 모델보다 BLEU 2.0 이상 높았다.
  >
  > 냥박사: 문장이 **아무리 길어도 정확하게** 번역해내는 능력이 엄청나거든.
- **원인:** 사실 문장과 근거는 코드가 붙여 정확하지만(3-2, 3-5), **대사는 검사하지 않았다.** 쉬운 비유를 만들수록 뜻이 바뀌기 쉽다.
- **해결:** 사실 컷 대사를 다 쓴 뒤, 사실·근거 원문과 대사를 함께 보여 주고 대사마다 **맞음·어긋남·덧붙임**으로 판정하게 했다. 어긋나면 이유를 알려 다시 쓰고, 끝까지 남으면 그 대사만 뺀다. 판정 예시는 특정 논문 낱말 없이 형식만 둔다(3-14에서 예시 낱말이 새어 나온 경험).
- **확인:** 188번의 두 대사를 같은 지시문으로 데스크탑 AI에 넣어 보니 둘 다 '덧붙임'("원문은 선형적 증가와 역제곱근 감소를 설명하므로 비유에 추가 정보(속도를 올리는 것)가 있다"). 189번에서는 같은 학습률 컷이 "학습률은 처음에 선형적으로 늘리고, 그 다음부터는 스텝 수 역제곱근에 비례해 줄였어."로 나왔다.
- **대가:** 대본 쓰기 64초 → 약 110초(컷마다 확인 요청 1번).
- **부작용(191번, 기록만):** 콩이의 "그렇다면 이 주의 집중 방식이 번역의 열쇠군요!"가 빠지자 이에 답하던 냥박사의 "맞아."만 남아 앞뒤가 끊겼다. 대사를 빼는 대신 컷 전체를 다시 쓰게 하는 방법이 있지만 시간이 더 든다.
- **배운 점:** "근거를 붙였다"와 "대사가 근거와 맞다"는 다른 보장이다. 검증이 필요한 곳은 AI가 **글을 새로 만드는 모든 곳**이다.

| 4-4 | 맥에서 데스크탑(집 네트워크 주소)에 `No route to host` | macOS가 앱마다 로컬 네트워크 접근을 따로 허락하는데, 터미널 도구(Anaconda python·curl)는 허락되지 않음 | 시스템 `/usr/bin/curl` 사용. IntelliJ(Java)는 허락돼 있어 정상 |
| 4-5 | `localhost`로 접속이 실패할 수 있음 | Docker를 IPv4 `127.0.0.1`에만 열었는데 Java가 `localhost`를 IPv6 `::1`로 먼저 찾음 | 설정에 `127.0.0.1`을 직접 적음 |
| 4-6 | 결과 파일에 `400 Bad Request` | 안내문의 `{id}`를 그대로 입력. curl은 중괄호를 특수 문자로 읽어 `id`로 바꿈 | `{id}` 자리에 실제 번호 입력 |
| 4-7 | 명령이 아무 반응 없이 멈춤 | 주소 오타 `177.0.0.1`(인터넷의 다른 컴퓨터). `curl -s`(조용히)가 기다리는 중이라는 표시도 숨김 | 주소 수정. 기다림이 의심되면 `--max-time`을 붙인다 |
| 4-8 | 저장한 만화 파일에 `409 Conflict` | 작업이 끝나기 전에 받음 | `COMPLETED` 확인 후 받기 |
| 4-9 | 터미널에서 띄운 두 번째 서버(Java)가 데스크탑에 `No route to host`, 맥북으로 넘어가 `model not found` | 4-4와 같은 원인. 터미널에서 실행한 Java는 로컬 네트워크 허락이 없음(IntelliJ의 Java만 허락됨). 맥 기본 python3도 막힘 | 시험 동안만 `127.0.0.1:11435`에 요청을 `/usr/bin/curl`로 넘기는 작은 연결 다리를 띄움. 처음엔 Java 기본 HTTP 클라이언트가 요청을 조각(chunked)으로 나눠 보내 다리가 빈 요청을 넘겼다(`missing request body`) → 조각 읽기 추가. 끝난 뒤 다리와 서버 모두 종료 |
| 4-10 | 작업이 끝날 때까지 기다리는 명령이 끝나지 않음 | 완료를 `DONE`으로 기다렸는데 API의 완료 상태는 `COMPLETED`(단계 이름 DONE과 상태 이름 COMPLETED가 다름) | `COMPLETED`·`FAILED`·`CANCELLED` 중 하나면 멈추게. 기다리는 조건에는 실패·취소도 넣는다 |
| 4-11 | zsh에서 `git add $F`가 파일 여러 개를 이름 하나로 봄 | zsh는 bash와 달리 변수 안의 공백으로 나누지 않음 | 파일 이름을 직접 나열 |
| 4-12 | 대본 쓰기 중에 취소하려던 시험이 그냥 완료됨(193번) | 진행 상태를 공백으로 잘랐는데 단계 이름 '대본 쓰기'에 띄어쓰기가 있어 숫자 자리를 못 읽음 | 공백이 아닌 구분 기호(세로선)로 자름. 화면용 한국어 이름보다 코드 값으로 비교하는 쪽이 안전 |

## 5. Git · 설정

| # | 증상 | 원인 | 해결 |
| --- | --- | --- | --- |
| 5-1 | 열흘치 작업이 한 번도 커밋되지 않음 | 기능 구현에만 집중 | 의미 단위 11개 커밋으로 정리. 각 커밋 시점의 코드가 컴파일되는 순서로 나눔 |
| 5-2 ⭐ | 집 데스크탑 주소와 DB 비밀번호가 설정 파일에 그대로 있음 | 설정과 비밀값을 구분하지 않음 | `.env`로 분리하고 git에서 제외, 양식은 `.env.example`로 커밋. 커밋 전에 기록 전체를 검사 |
| 5-3 | GitHub `main`에 올렸는데 새 브랜치만 생김 | 저장소를 만들 때 README가 자동 생성돼 GitHub `main`이 별개의 기록이 됨 | 원격이 그 README 커밋일 때만 덮어쓰도록(`--force-with-lease`) 해서 `main`을 맞춤 |
| 5-4 ⭐ | 커밋에서 파일을 빠뜨려도 내 컴퓨터의 테스트는 통과 | 새 파일(V2 SQL, 새 테스트)은 `git add` 전까지 git이 모르는 파일(`??`)이지만 폴더에는 있어 로컬 테스트는 돈다. 빠뜨리면 GitHub의 코드는 서버가 켜지지 않는다(V2가 없으면 `plan_json` 칸이 없어 검사 실패) | GitHub Actions CI로 push마다 다른 컴퓨터에서 테스트. 넣기 전에 커밋된 코드만 다른 폴더(git worktree)에 꺼내 `.env` 없이 돌려 비밀 정보 없이도 통과하는지 확인(117개). 외부 액션은 커밋 번호로 고정, 읽기 권한만 |
| 5-5 | 커밋 뒤 비밀 정보 검사가 2건을 찾음 | 찾은 것은 커밋하지 않은 문서의 `127.0.0.1`·`0.0.0.0`(비밀 아님). 검사 범위가 커밋할 파일보다 넓었음 | 검사는 커밋 **전에**, 커밋할 파일만 대상으로. 찾은 줄은 직접 보고 판단 |
| 5-6 | 실행 결과 파일에 논문 원문 문장이 많이 들어 있음 | 근거 원문까지 담은 API 결과를 그대로 저장해 커밋 | 결과 파일(`results/`, `spikes/llm-spike/results/`)은 저장소에서 빼고(`git rm --cached`, 파일은 이 컴퓨터에 남김) `.gitignore`에 추가. 개선 내용과 숫자는 문서로만 설명. 예전 커밋 기록에는 남아 있음(비공개 저장소) |
